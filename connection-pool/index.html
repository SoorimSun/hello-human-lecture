DB 커넥션 풀은 왜 고갈될까?

Spring 애플리케이션은 요청을 처리할 때 DB 커넥션을 풀에서 빌려 쓰고 다 쓰면 돌려줍니다. 빌려 간 커넥션이 제때 돌아오지 않으면 다음 요청은 줄을 서고, 너무 오래 기다린 요청은 실패합니다. 아래 작업대 모형에서 요청이 몰리는 정도와 처리 시간을 직접 바꿔 보세요.

교육용 단순 모델입니다

이 화면은 실제 데이터베이스에 연결하지 않습니다. HikariCP 같은 실제 커넥션 풀의 내부 구현을 재현한 것도 아닙니다. 개념이 잘 보이도록 규칙을 아래 네 가지로 줄였습니다.

  1. 커넥션은 10개로 고정되어 있습니다.
  2. 요청 하나는 커넥션 하나를 쓰고, 처리가 끝나면 바로 반환합니다.
  3. 커넥션이 모두 사용 중이면 먼저 온 요청부터 줄을 섭니다(FIFO).
  4. 2초 안에 커넥션을 얻지 못한 요청은 타임아웃으로 실패합니다.

요청은 일정한 간격으로 도착하고, 처리 시간은 모든 요청이 같다고 가정합니다.

모형 읽는 법

요청 카드
처리해야 할 요청 하나입니다. 왼쪽 위 매거진에서 일정한 간격으로 나옵니다. 매거진 앞면의 숫자는 지금까지 도착한 요청 수입니다.
대기 컨베이어
커넥션을 기다리는 줄입니다. 카드는 기다린 시간만큼 오른쪽으로 가고, 아래 눈금은 0.1초 간격입니다. 길이가 정확히 2초라서 끝까지 간 카드는 타임아웃입니다. 맨 오른쪽 카드가 가장 오래 기다린 줄의 맨 앞입니다.
칸 10개
커넥션 10개입니다. 칸마다 뒤쪽 덕트로 DB 드럼에 이어져 있습니다. 카드가 칸에 있으면 사용 중, 빈 칸은 유휴입니다.
램프와 막대
칸 앞면의 램프가 검게 켜지면 사용 중입니다. 막대는 처리가 얼마나 진행됐는지 보여 줍니다.
완료 트레이
처리를 마친 카드가 떨어지는 곳입니다. 카드가 칸을 떠나는 순간 커넥션이 반환되고, 줄의 맨 앞 카드가 그 칸을 받습니다.
타임아웃 통
2초를 넘긴 카드가 떨어집니다. 통 앞면의 빨간 숫자가 타임아웃 누적 수입니다.
조작함
왼쪽 손잡이는 유입량, 오른쪽 손잡이는 처리 시간을 가리킵니다. 스위치는 일시정지, 버튼은 초기화와 함께 움직입니다.

왜 고갈될까?

한꺼번에 필요한 커넥션 수는 대략 다음과 같습니다. 대기열 이론에서 리틀의 법칙이라고 부르는 관계입니다.

필요한 커넥션 수 ≈ 초당 요청 수 × 요청 하나가 커넥션을 쥐고 있는 시간

1초에 10건이 들어오고 하나가 0.5초씩 커넥션을 쥐면 평균 5개면 충분합니다. 그런데 쿼리가 느려져 1.6초씩 쥐게 되면 16개가 필요합니다. 풀에는 10개뿐이니 나머지 요청은 줄을 서야 합니다.

줄은 저절로 줄어들지 않습니다. 풀이 1초에 처리할 수 있는 양은 10개 ÷ 처리 시간입니다. 이보다 많이 들어오는 만큼 대기열이 길어지고, 2초를 넘긴 요청부터 실패합니다. 이 상태가 계속되면 1초에 대략 유입량 − 10 ÷ 처리 시간건이 타임아웃됩니다. 예를 들어 10건/초 × 1.6초라면 1초에 6.25건만 처리되고 약 3.75건이 실패합니다.

그래서 풀 고갈은 커넥션의 개수보다 커넥션을 쥐고 있는 시간 때문에 생기는 경우가 많습니다. 처리 시간이 두 배가 되면 필요한 커넥션도 두 배가 됩니다.

직접 해 보기

  1. 여유를 눌러 보세요(10건/초 × 0.5초 = 5개). 램프가 다섯 개 안팎만 켜지고 컨베이어는 비어 있습니다.
  2. 느린 쿼리를 눌러 보세요(10건/초 × 1.6초 = 16개). 유입량은 같은데 램프 10개가 모두 켜지고, 카드가 컨베이어에 쌓이다가 2초 끝에서 통으로 떨어지기 시작합니다.
  3. 요청 폭주를 눌러 보세요(30건/초 × 0.5초 = 15개). 처리는 빠르지만 들어오는 양이 많아 역시 고갈됩니다.
  4. 고갈된 상태에서 처리 시간을 0.5초 이하로 내려 보세요. 쌓였던 줄이 얼마나 빨리 풀리는지 볼 수 있습니다.
  5. 어떤 상황에서도 사용 중 + 유휴는 항상 10입니다. 커넥션 수는 그대로이고 쓰임만 바뀌기 때문입니다.

Spring 애플리케이션에서는

Spring Boot는 따로 정하지 않으면 HikariCP를 커넥션 풀로 씁니다. 풀 크기와 커넥션을 기다리는 최대 시간은 설정으로 바꿀 수 있습니다.

# 풀의 최대 커넥션 수 (HikariCP 기본값 10)
spring.datasource.hikari.maximum-pool-size=10
# 커넥션을 얻으려고 기다리는 최대 시간, 밀리초 (기본값 30000 = 30초)
spring.datasource.hikari.connection-timeout=30000

이 모형은 풀 크기 10을 그대로 두고, 대기 한도만 화면에서 보기 쉽게 2초로 줄였습니다. 설정 이름과 개념을 빌려 왔을 뿐, HikariCP가 대기자를 고르는 순서나 커넥션을 만들고 검사하고 돌려받는 방식은 재현하지 않았습니다.

실제 애플리케이션에서 대기 한도를 넘기면 로그에 Connection is not available, request timed out after 30000ms 같은 문구가 남습니다. 이런 문구를 보면 다음을 먼저 의심해 보세요.

  • 느린 쿼리. 인덱스가 없거나 너무 많은 데이터를 읽으면 처리 시간이 길어집니다.
  • 트랜잭션 안의 오래 걸리는 일. @Transactional 메서드 안에서 외부 API를 호출하거나 파일을 다루면, 그동안 커넥션을 쥐고 있을 수 있습니다.
  • 요청 급증. 이벤트나 배치 작업으로 유입량이 갑자기 늘어납니다.
  • 반환 누락(커넥션 누수). 직접 연 커넥션을 닫지 않으면 풀로 돌아오지 않습니다. 이 모형은 항상 반환하므로 누수는 다루지 않습니다.

대응은 보통 커넥션을 쥐는 시간을 줄이는 것부터 시작합니다. 쿼리를 개선하고 트랜잭션 범위를 좁히는 식입니다. 풀 크기를 키우면 DB가 동시에 받는 부하도 커지므로, DB가 감당할 수 있는 범위에서 측정하면서 조정하세요.

이 모형이 단순화한 것

  • 요청은 일정한 간격으로 오고 처리 시간은 모두 같습니다. 실제 트래픽은 몰렸다 빠졌다 하므로, 평균으로는 여유가 있어도 순간적으로 고갈될 수 있습니다.
  • 커넥션을 새로 만들거나 검사·교체하는 과정이 없습니다. 최소 유휴 수나 커넥션 수명 같은 설정도 없습니다.
  • 먼저 온 요청부터 받는 것(FIFO)은 이 모형의 규칙입니다. 실제 풀 구현의 대기 순서는 다를 수 있습니다.
  • 대기 한도 2초는 화면에서 보기 쉽게 정한 값입니다. HikariCP의 기본값은 30초입니다.
  • 요청을 처리하는 스레드 수나 DB 자체의 처리 능력은 그리지 않았습니다.

숫자는 어떻게 계산하나요?

화면의 모든 숫자(사용 중·유휴·대기·타임아웃)와 카드·램프의 움직임은 한 시뮬레이션 모델에서 나옵니다. 사용 중은 사용 중인 커넥션 목록에서, 유휴는 유휴 커넥션 목록에서 따로 셉니다. 요청이 도착하거나 커넥션을 얻거나 반환하거나 타임아웃될 때마다 ‘사용 중 + 유휴 = 10’을 포함한 규칙을 다시 확인하고, 그 결과를 수치 패널에 표시합니다.

교육용 단순 모델 · 실제 데이터베이스나 HikariCP의 내부 구현이 아닙니다.
